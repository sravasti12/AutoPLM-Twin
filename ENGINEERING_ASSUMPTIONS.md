# Synthetic engineering and simulation assumptions

All manufacturers, suppliers, parts, platforms, signals and release records are fictional. The data models do not claim compatibility with real automotive standards or production control units.

1. Each generated platform has speed sensor, gateway, brake and cluster functions on a connected fictional CAN network. `speed.v1` is an abstract signal contract. Interface strings are compatibility labels, not physical bus implementations.
2. Even-numbered fleets have released revision B, version 2.10.0 and speed.v1; odd-numbered fleets have revision C, version 3.0.0 and speed.v2. Each has an approved revision change effective 2025-01-01. Two trims use each fleet's ECU architecture. BOMs contain a root, a controls subassembly and four leaves with quantity one.
3. BOM edges model unique part occurrences as a rooted tree. Multiple parents and duplicate edges are rejected. Leaf quantity roll-up multiplies quantities along paths. Subassembly revision catalogs, weights and manufacturing tolerances are not modeled.
4. Hardware revisions use single-letter alphabetic ordering. Software versions use PEP 440 parsing and semantic numeric comparison. Dependency identifiers are exact releases; version ranges are future work.
5. Required software dependencies must exist globally and be installed in the variant. Interface and revision allowlists must be explicitly satisfied. Absence of installed hardware/software fails closed.
6. The default engineering as-of date is fixed at 2025-06-01. This is an evaluation convention, not wall-clock effectivity. Released changes and BOMs must already be effective at that date.
7. The twin includes vehicle/ECU/software configuration, network topology, applicable BOMs, related change records and initial OFF states. Exact comparisons flag ordering changes in lists as discrepancies; graph isomorphism or semantic set normalization is not implemented. Duplicate records can collapse in twin identity maps; the independent duplicate rule detects this.
8. ECU state transitions are OFF (snapshot) → INITIALIZING → READY → ACTIVE. Initialization fails on missing components/platform, unsupported hardware revision, software allowlist or required interfaces. An unavailable speed signal produces DEGRADED consumers. These behaviors are invented explicitly for this prototype.
9. Initialization takes 0.1 abstract simulation seconds. At one-second intervals the speed sensor publishes `50 - 2*tick` km/h. A gateway relays the latest value; brake and cluster consume it over available topology paths. Tasks run sensor, gateway, brake, cluster in deterministic order with zero transport delay. This ordering is a modeling assumption, not a timing validation.
10. The fictional brake command is a Boolean indicating a positive available speed. It does not represent stopping distance, pressure, wheel slip, actuator state or actual automotive control behavior. No safety claim can be inferred from this signal.
11. A runtime outage at tick N suppresses sensor messages from that tick onward; gateway, brake and cluster become DEGRADED. Events preserve abstract time, component, state and signal.
12. A broken BOM can have normal signal behavior while failing engineering validation. A wrong software version string can remain behaviorally compatible if modeled interfaces and revisions are unchanged; source reconciliation still detects the migration defect. A schema-valid mass conversion error is a reconciliation defect, not a physical simulation effect.
13. Simulation results are diagnostic and never substitute for engineering approval. Migration approval currently requires source reconciliation and twin equality, while behavioral traces are separately inspectable evidence.
14. Repairs restore source references. If the source is itself incompatible, deterministic revalidation rejects restoration. New engineering configurations require a separately reviewed source/change process.
